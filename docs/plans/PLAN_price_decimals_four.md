## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

**`signals.csv` 의 종가가 차트 숫자와 미세하게 어긋난다.**

2026-08-20 대조 3단계에서 실제로 드러났다. QQQ 원본가로 전환해 "종가가 차트와 그대로 맞는다"가 전제가 됐는데, 정작 파일에는 이렇게 적혀 있다.

| 날짜 | `signals.csv` 실제 값 | 차트·문서 값 |
| --- | --- | --- |
| 2020-03-16 | `169.300003` | `169.30` |
| 2020-03-12 | `177.320007` | `177.32` |
| 2008-10-13 | `35.130001` | `35.13` |
| 2008-10-28 | `31.860001` | `31.86` |

**차이의 정체는 부동소수점 표현 잡음이다.** yfinance 가 32비트 실수로 내려주는 값을 6자리까지 그대로 적으면서 `.000003`, `.000007` 같은 꼬리가 남았다. 실제 시세에 그런 자리는 존재하지 않는다. **4자리로 접으면 전부 사라진다** — `169.300003 → 169.3`, `177.320007 → 177.32`.

원본가 전환(§7 결정 ⑰)의 목적이 "사용자가 차트와 직접 대조할 수 있게 한다"였는데, 자릿수가 그 목적을 절반만 달성한 상태다.

### 왜 안전한가 — 착수 전 실측 (2026-08-20, QQQ 6,903행)

**자릿수를 줄이면 판정이 바뀔 수 있다.** 그래서 착수 전에 전 구간으로 재 봤다.

| 확인 | 결과 |
| --- | --- |
| 원시 값이 실제로 바뀌는 행 | **6,692 / 6,903 (97%)** — yfinance 는 6자리를 거의 다 쓴다 |
| 등락률 최대 절대차 | **1.9e-06** (0.00019%p) |
| 등락률 **부호**가 바뀌는 날 | **0건** → 테스트 B(연속 등락) 판정 불변 |
| 등락률이 **정확히 0** 인 날 | 38건 → 38건 (불변) → 결정 ⑧(0% 등락일 처리) 영향 없음 |
| **확장창 상위 10위 판정**이 달라지는 날 | **0건** (폭락 65일·폭등 66일 대상) → 테스트 A 신호 불변 |
| 등락률 표시값(2자리)이 달라지는 날 | **3건** — 2011-02-01, 2012-08-03, 2021-08-26. 셋 다 신호일이 아니다 |
| 등락률 동률쌍 | 51 → 72 로 늘어난다. 확장창 순위는 **동률에 같은 순위를 주므로**(결정 ⑪ 아님, 이벤트 정의 계약) 신호 수에 영향이 없고, 위의 "상위 10위 판정 0건 변화"가 그것을 확인한다 |

**즉 신호 판정은 하나도 바뀌지 않고, 종가 표기만 깨끗해진다.** 수익률은 소수 6~7째 자리에서 미세하게 달라지나 백분율 2자리 표시에서는 사실상 같다.

### 왜 지금 해도 되는가 — 재수집 타이밍

`yfinance_collector.RECENT_EXCLUSION_DAYS = 2` 이고 컷오프가 `date.today() - 2일` 이다. 오늘이 **2026-08-20** 이므로 재수집해도 QQQ 끝 날짜는 **2026-08-18 그대로**다. **기간이 늘어나지 않으므로 대조 기준값이 흔들리지 않는다.**

반대로 국내는 컷오프가 `오늘 − 1일` 이라 지금 받으면 2026-08-11 → 2026-08-19 로 늘어난다. 그래서 이번에는 받지 않는다(비목표 1).

### 왜 상수를 통합해야 하는가

자릿수 6 은 **두 계층에 따로 정의돼 있다.**

| 위치 | 상수 | 무엇을 정하나 |
| --- | --- | --- |
| `src/verify_lab/data/yfinance_collector.py:40` | `PRICE_DECIMALS = 6` | 원시 시세 파일에 적히는 자릿수 |
| `src/verify_lab/studies/index_extreme/constants.py:111` | `PRICE_DECIMALS_DECIMAL = 6` | 결과 CSV 의 종가 표시 자릿수 |

둘은 같은 규칙(`.claude/rules/python.md` 규칙표의 "소수 가능 가격")에서 나오고 **반드시 같은 값이어야 한다.** 저장이 4자리인데 출력이 6자리면 없는 정밀도를 만들어 내고, 반대면 저장해 둔 값을 버린다. 그런데 지금은 한쪽만 바뀌어도 **예외가 나지 않는다.**

`src/verify_lab/CLAUDE.md` "상수 관리"가 이 상황을 이미 규정하고 있다 — *"2개 이상 계층에서 사용 → `common_constants.py`"*, *"계층 간 중복 정의는 발견 즉시 통합합니다."* 이번 변경이 정확히 그 발견의 계기다. 두 곳을 동시에 고쳐야 한다는 사실 자체가 중복의 증거다.
