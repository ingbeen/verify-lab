## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

- `.env` 에 `KRX_ID`·`KRX_PW` 가 준비돼 있지만 **pykrx 는 `.env` 를 읽지 않는다.** 환경 변수만 본다.
  지금 상태로는 국내 데이터를 한 줄도 받을 수 없다
- **`import pykrx` 하는 것만으로 로그인 시도가 일어난다**(실측, Notes 참고). 따라서 자격증명 로딩은
  "먼저 부르면 좋은" 것이 아니라 **import 보다 앞서야 하는 순서 제약**이다. 이 순서는 사람이 기억할 게 아니라
  코드 구조로 강제해야 한다
- 스펙 §9 에 "착수 전 실측이 필요한 항목" 5개가 미확인으로 남아 있다. 그중 **분배금 조정 여부**는
  KODEX 200 수집기의 설계를 통째로 바꾸는 항목이다 — 조정되지 않았다면 별도 처리가 필요하다
- 로더만 따로 만들면 **호출처가 0건**이라 실제로 로그인이 되는지 확인할 방법이 없다.
  실측 스크립트와 한 묶음으로 진행해야 로더가 검증된다

## 7) 리스크(Risks)

- **import 순서가 깨질 위험** — `import pykrx` 만으로 로그인 시도가 일어나므로(실측), 누군가 모듈 최상단에
  pykrx import 를 옮기면 자격증명 없이 로그인이 시도된다. 완화책은 **import 를 함수 안에 두고 그 이유를 주석으로 남기는 것**
- **로그인 ID 가 표준 출력에 찍히는 위험** — pykrx 가 성공/실패 시 로그인 ID 를 print 한다(실측).
  비밀번호는 찍지 않는다. 실행 로그를 공유하거나 문서에 붙일 때 그 줄을 빼야 한다.
  스크립트 docstring 과 `docs/COMMANDS.md` 에 경고를 남긴다
- **전 기간을 한 번에 못 받을 위험** — 20여 년 구간을 한 번에 주는지 확인된 바 없다.
  분할 로직을 미리 만들지 않는다(YAGNI). 실패하면 **그 사실 자체가 실측 결과**이며 다음 계획서에서 다룬다
- **레이트리밋·차단 위험** — KRX 호출을 5회 내외로 유지하고 재시도·백오프를 넣지 않는다
- **분배금 조정 여부 판정이 빗나갈 위험** — 판정 방법(Notes 결정 ④)이 "조회 종료일을 달리해 같은 날을 두 번 받는"
  간접 방식이다. 결과가 애매하면 단정하지 않고 "판정 보류"로 기록하고 사용자에게 보고한다
