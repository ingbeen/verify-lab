## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

`VALIDATION_LINE` 이 **문서 전체에서** `validate_project.py` 가 든 체크박스 줄을 찾는다.
그래서 «기록»과 «기록이 아닌 것»을 구분하지 못하고, 오류가 **양방향**으로 난다.

| 방향 | 무엇이 벌어지나 |
| --- | --- |
| **누락** | 옛 템플릿 DoD 의 설명 문구 `(failed=0, skipped=0; passed/failed/skipped 수 기록)` 를 **결과 값으로 읽어**, 품질 검증을 한 번도 돌리지 않아도 통과한다 |
| **오탐** | 작업 지시 줄(「그 스크립트 안내 문구를 고친다」)을 **실행 기록으로 오인**한다. 직전 계획서가 Done 직전에 실제로 여기 걸려 문구를 바꿔야 했다 |

둘은 같은 뿌리다 — **무엇이 「기록」인지 정의하지 않았다.**

### 실측 (2026-09-10)

워크스페이스 3개 저장소의 Done 계획서 **25건** 전수.

| 잰 것 | 결과 |

| 계획서당 `VALIDATION_LINE` 에 걸리는 줄 | **2개** (Validation 절 안 1 · DoD 문구 1) |
| Validation 절이 아예 없는 계획서 | 1건 (`quant/PLAN_late_entry_sizing_review.md`, **이미 다른 사유로 막혀 있다**) |
| **`passed=<숫자>` 가 든 줄이 하나도 없는 계획서** | **0건** |

### 왜 더 단순한 쪽인가 — 🔴 이 판단은 «틀렸다» (§8 참고)

> 아래는 계획 수립 시점의 판단이고 **코드 리뷰에서 뒤집혔다.** 기록으로 남긴다 —
> 결론만 고치면 같은 함정을 다시 밟는다.

직전 계획서의 코드 리뷰는 근본 해결로 **「마지막 Phase 의 `**Validation**` 절 안쪽으로 검색 범위를 한정」**을 제안했다. 그런데 실측해 보면 **`passed=<숫자>` 를 요구하는 것만으로 같은 결과**가 나온다.

| | `passed=숫자` 요구 | Validation 절 앵커링 |
| --- | --- | --- |
| 코드 | **필터 한 줄** | 절 범위 파싱 (약 15줄) |
| 누락 방향 | 막힘 | 막힘 |
| 오탐 방향 | 막힘 | 막힘 |
| 기존 계획서 | **0건 영향** | 1건이 새로 걸림 |

**설명 문구에는 `passed=` 뒤에 숫자가 오지 않는다**(`passed/failed/skipped 수 기록`). 작업 지시 줄에도 없다.
실행 기록에만 있다. 그래서 이 한 조건이 「기록」의 정의가 된다.

## 7) 리스크(Risks)

- **`passed` 를 안 적고 `failed`·`skipped` 만 적는 관행이 있으면 기록이 인정되지 않는다.**
  실측상 25건 전부 `passed` 를 적고 있어 지금은 문제가 없다. Phase 0 회귀 케이스가 이를 고정한다
- **여전히 「기록처럼 보이게」 적으면 통과한다.** 절 앵커링도 같은 성질이므로 이 축에서는 차이가 없다.
  기계가 막을 수 있는 것은 「안 적은 것」이지 「거짓으로 적은 것」이 아니다
- 훅은 어느 저장소의 Ruff·PyRight 검사도 받지 않는다. Phase 마다 직접 실행을 Validation 으로 둔다
- `~/.claude/` 변경은 다른 PC 로 자동으로 넘어가지 않는다. `claude-config-export`/`import` 로 옮기며 이번 범위는 아니다

| 절 앵커링을 버린 이유(실측 비교) | 같은 주석 한 줄 |
| 작성자가 지켜야 할 규격(수를 적어야 기록으로 센다) | `SKILL.md` 의 `[중요]` 안내 |

### 설계가 뒤집힌 경위 (승인받음)

계획서는 **`passed=<숫자>` 토큰**으로 기록을 가르기로 했고, 리뷰가 제안한 **Validation 절 앵커링**을
「더 단순한 방법으로 같은 결과」라며 물렸다. **코드 리뷰가 그 판단을 무너뜨렸다.**

| 리뷰가 잡은 것 | 토큰 방식 | 절 앵커링 |
| --- | --- | --- |
| 🔴 **실패를 정직하게 적은 기록이 조용히 통과** (`failed=3`) — 내가 만든 회귀 | 발생 | 없음 |
| `(failed=0, skipped=0)` 만 적은 정직한 기록에 **「기록이 없습니다」라는 거짓 메시지** | 발생 | 없음 |
| **작업 지시 줄이 `passed=53` 을 «인용»하면 게이트가 열림** — 없애려던 오탐 유형 그대로 | 발생 | 없음 |
| Done 규칙에 없던 `passed` 를 **새로 요구** | 발생 | 없음 |

**내가 잰 것은 「기존 계획서가 안 깨지는가」였지 「정의가 옳은가」가 아니었다.**
리뷰 표현대로 토큰 방식은 **구조가 아니라 대리물**이다. 사용자 승인 후 절 앵커링으로 전환했고,
네 가지가 전부 사라졌다.

**교훈은 「자리로 가른다」이다.** 「기록처럼 보이는 줄」을 모양으로 가르려 하면 인용을 구별할 수 없다.

### 미조치 1건

**실패한 1차 실행과 통과한 재실행을 «둘 다» 적으면 Done 이 막힌다.** 절 안의 모든 기록을 검사하므로
`(failed=2)` 줄이 위반으로 잡힌다. 고정 규칙이 「실패하면 즉시 수정 후 재검증한다」이므로 두 줄로
남기는 것이 정석인데, 지금은 실패 기록을 지워야 통과한다.

고치려면 **마지막 기록으로 판정**하거나 **깨끗한 기록이 하나라도 있으면 통과**시키면 된다.
이번 범위 밖으로 두었다 — 실제로는 최종 실행만 적어 왔다.

### 이 계획서 자신이 사례다

직전 계획서(`PLAN_plan_lint_gate_holes`)가 Done 직전에 **오탐 방향에 걸렸다** — Phase 2 의 작업 지시 줄에
스크립트 이름이 들어갔다는 이유로 「실행 기록인데 수가 없다」는 위반이 났고, 문구를 바꿔 우회했다.
**우회가 아니라 정의를 세워 푸는 것이 이 계획서다.**
