## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

- `src/verify_lab/measure/` 가 비어 있어 **"신호 다음에 실제로 무슨 일이 있었나"를 잴 수단이 없다.**
  데이터(Phase 1)는 전부 확보됐고 다음 병목이 여기다
- forward return 은 **정의가 곧 결론을 만드는** 계층이다. 기준점을 하나만 두거나 출구를 다르게 잡으면
  "갭으로 새는 몫"이라는 §7 결정 ⑥ 의 해석 자체가 성립하지 않는다
- 측정 구간 끝이 데이터를 넘어가는 신호를 조용히 버리면 **생존편향**이 생긴다.
  국내는 2026년 신호가 상위 10위의 60%를 차지하고 그 신호들의 측정 구간이 아직 끝나지 않았으므로,
  이 처리가 실제로 대량 발생한다 — 이론적 위험이 아니다
- look-ahead 는 눈으로 발견되지 않고 성과만 좋아 보이게 만든다. 이벤트 정의가 생기기 **전에**
  감시 계약을 만들어 둬야 이후 모든 정의가 같은 검사를 통과한다

- **두 기준의 출구를 다르게 잡을 위험** — 익일 시가 기준의 출구를 `t+1+h` 로 두면 구간 길이가 달라져
  "차이 = 갭"이라는 해석이 무너진다. 출구는 양쪽 모두 `Close[t+h]` 다. 테스트로 고정한다
- **거래일과 달력일을 섞을 위험** — 측정 구간은 전부 거래일이다. 날짜 연산이 아니라
  **위치 인덱스 shift** 로만 계산해 구조적으로 막는다
- **look-ahead 감시 계약을 잘못 쓸 위험** — forward return 은 정의상 미래를 본다.
  "잘라도 결과가 전부 같다"로 쓰면 항상 실패한다. 계약은 **짧은 입력에서 값이 있는 칸에 한정**된다
- **long-form 이 행 수를 12배로 늘리는 부담** — 신호 수십 건에서는 무의미하고,
  2-b 의 단순 보유 베이스라인(전 거래일 ≈ 6,900일)에서도 8만 행 수준이라 벡터 연산으로 충분하다
- **상수 위치가 곧 바뀔 위험** — 현재 `measure/` 에 파일이 하나뿐이라 상수는 파일 상단이 규칙에 맞다.
  2-b 가 같은 구간 상수를 쓰기 시작하면 그때 `measure/constants.py` 로 승격한다 (2계층 이상 아님)
