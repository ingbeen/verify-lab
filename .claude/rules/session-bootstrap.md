# 세션을 시작할 때

> 이 문서에는 `paths` frontmatter 가 없다. **매 세션 조건 없이 로드된다.**
> 내용을 쌓지 않고 **어디를 봐야 하는지만** 적는다 — 지식을 복사하면 두 벌이 되고 한쪽이 낡는다.

## 1. 무조건 — 첫 작업 전에 문서 지도를 연다

**[docs/INDEX.md](../../docs/INDEX.md) 를 `Read` 도구로 연다.**

무엇이 어디 있는지가 거기 있다. `Read` 로 여는 이유는 아래 3절에 있다 — 셸로 읽으면
그 경로의 규칙이 함께 주입되지 않는다.

## 2. 조건부 — 작업 성격에 따라 이어 읽는다

| 이번 세션에 할 일 | 더 읽을 것 |
| --- | --- |
| **검증·측정·결과 문서** | 그 검증의 `docs/spec/<검증명>.md` → `docs/context/` 두 문서 |
| **매매 규칙** | `docs/strategy/<규칙명>.md` §1 (확정 규칙) → `.claude/rules/strategy.md` |
| **패키지 코드** | `src/verify_lab/CLAUDE.md` — 특히 「계층 간 계약」 |
| **하네스 설정·문서 정리·단순 질의응답** | 1 절에서 멈춘다 |

**전부 읽지 않는다.** 필요 없는 문서를 여는 것도 비용이다.

## 3. 이미 밟은 함정은 각 검증의 spec 에 있다

함정 목록을 여기에 두지 않는다. **원본이 있는 곳을 본다.**

| 찾는 것 | 어디 |
| --- | --- |
| 데이터 소스의 성질, 라이브러리 동작, 품질 문제 | `docs/spec/<검증명>.md` 「데이터 실측 기록」 |
| 왜 그 설계로 정했나, 무엇을 버렸나 | `docs/spec/<검증명>.md` 「확정된 설계 결정」 |
| 측정 결과를 어떻게 읽나, 무엇이 한계인가 | `docs/research/<검증명>.md` 「한계」·「해석」 |
| 판정 기준·측정의 원칙 | 루트 `CLAUDE.md` |

## 4. 규칙 자동 로드는 `Read` 도구에만 걸린다 (실측 2026-08-09 · 2026-08-29)

**결과: `paths:` frontmatter 자동 로드는 동작한다. 트리거는 편집이 아니라 `Read` 도구다.**

| 패턴 | 읽은 파일 | 주입된 것 |
| --- | --- | --- |
| `**/*.py` | `src/verify_lab/utils/logger.py` | `.claude/rules/python.md` + `src/verify_lab/CLAUDE.md` |
| `docs/**` | `docs/` 의 문서 | `.claude/rules/docs.md` |

판별에는 **그 규칙 문서에만 있고 다른 곳에는 없는 값**을 썼다(반올림 자릿수, 스펙과 결과의 분리).
다른 문서에는 "python.md 를 따른다" 같은 포인터만 있고 값이 없다.

### 구멍은 둘이다

| 구멍 | 언제 | 대응 |
| --- | --- | --- |
| **1. 새 파일부터 만든다** | 기존 파일을 열지 않으면 주입될 것이 없다 | 해당 규칙 문서를 직접 연다 |
| **2. 셸로 읽는다** | `cat`·`head`·`sed -n` 은 주입을 걸지 않는다 | **코드 파일은 `Read` 도구로 연다.** 셸은 검색·집계에 쓴다 |

**구멍 2 는 auto 모드에서 특히 위험하다.** auto 모드가 "파일은 `cat`·`head`·`sed -n` 으로 읽어라"를
지시하므로, 그 모드에서는 경로 규칙이 **한 번도 안 걸린 채 작업이 끝날 수 있다.**

실측(2026-08-29): 같은 `.py` 파일을 셸(`cat -n`)로 읽었을 때는 규칙이 주입되지 않아
"검색해야만 알 수 있다"고 답했고, `Read` 도구로 열었을 때는 검색 없이 답했다.

> **"규칙이 로드됐냐"고 그냥 물으면 안 된다.** `CLAUDE.md` 에 적힌 "자동 로드된다"는 문장을
> 근거로 추측해 답하기 때문이며, 실제로 그런 오답이 나왔다. **그 규칙 문서에만 있는 구체적 값**을
> 묻고 "파일을 추가로 열지 말고 추측하지 말라"는 제약을 함께 건다.

## 5. 품질 검증이 전부 실패하면 코드가 아니라 환경을 먼저 본다 (실측 2026-08-10)

**증상**: `validate_project.py` 가 Ruff·PyRight·Pytest 를 **모두** 실패로 보고하면서
`Command not found: ruff` 를 함께 출력한다. 실패 개수는 1개씩이고 Pytest 는 `passed=0` 이다.

**원인**: 셸에 `VIRTUAL_ENV` 가 프로젝트 밖 인터프리터로 설정돼 있으면 Poetry 2.x 가
**이미 활성화된 그 환경을 우선**하고, `virtualenvs.in-project = true` 로 만들어진 `.venv` 를 쓰지 않는다.
그 환경에는 개발 의존성이 없으므로 도구를 찾지 못한다.

**확인**: `poetry env info --path` 가 프로젝트의 `.venv` 를 가리키는지 본다.
다른 경로가 나오면 `VIRTUAL_ENV` 를 해제하고 실행한다(`env -u VIRTUAL_ENV`).

> 코드가 아니라 실행 환경 문제다. **품질 게이트가 통과하는데도 실패로 보이는 유일한 알려진 경로**이므로,
> 이 출력을 보면 코드를 고치기 전에 환경부터 확인한다.

## 6. `storage/results/` 는 다른 PC 로 넘어가지 않는다

git 제외 대상이라 **재생성은 되지만 동기화는 안 된다.**

- 결과 문서를 쓰거나 고치려면 **그 PC 에서 검증을 다시 실행**해야 한다
- 그때 **시세를 재수집하면 안 된다.** 기간이 늘어 신호 수와 성적이 달라지고,
  기존 결과 문서의 수치가 그 시점부터 재현되지 않는다
- 부득이 재수집했다면 **새 데이터 기준일과 무엇이 달라졌는지**를 해당 결과 문서에 적는다

## 7. Git 은 사용자가 직접 한다

`add`·`commit`·`push` 를 하지 않는다. 커밋 메시지 후보가 필요하면 `/commit` 스킬을 쓴다.
