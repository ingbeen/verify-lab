# docs 폴더 규칙

`docs/`는 verify-lab의 설계 문서, 검증 결과, 변경 계획서를 관리한다.

## 문서의 두 종류

| 종류 | 파일 | 수명 |
| --- | --- | --- |
| **살아있는 문서** | `ROADMAP.md`, `COMMANDS.md`, `context/*.md`, `spec/*.md`, `research/<검증명>.md` | 영구. 계속 갱신한다 |
| **계획서** | `plans/PLAN_*.md` | **임시.** 사용자가 주기적으로 전부 삭제한다 |

각 문서의 SoT 역할:

- `INDEX.md` — **저장소 전체의 문서 지도.** `docs/`·`reference/`에 파일을 추가·삭제·이동하면
  여기도 함께 고친다 (`docs/plans/` 는 예외). `tests/test_index.py` 가 양방향으로 검사하므로
  누락하면 `validate_project.py` 가 실패한다. 규칙 내용을 복제하지 말고 **위치만** 적는다
- `context/` — **사용자의 현재 운용 상태와 이 프로젝트가 시작된 이유.** 사용자가 갱신하는 문서이며
  AI가 임의로 수정하지 않는다. 작업 전에 읽는다 (`context/README.md`가 안내)
- `ROADMAP.md` — 검증 대상 목록, 진행 상태, Phase별 산출물, 계획서 승격 목적지
- `spec/<검증명>.md` — 개별 검증의 **확정 설계와 데이터 실측 기록**.
  확정된 결정뿐 아니라 **탈락안과 그 이유**를 함께 남긴다. "이미 해봤다"의 근거가 된다
- `research/<검증명>.md` — 측정 결과와 판정. 작성 규칙은 `docs/research/CLAUDE.md`
- `COMMANDS.md` — 모든 실행 명령어. 설치용 일회성 명령어는 제외하고 평상시 반복 실행하는 것만 둔다

## 아카이브 폴더를 만들지 않는다

`docs/archive/` 같은 **지난 버전 보관 폴더를 두지 않습니다.** 문서를 옮겨 쌓아두는 대신,
**남길 가치가 있는 과거 이력은 살아있는 문서 본문에 적습니다.**

- 설계가 바뀌었으면 `spec/`의 "확정된 설계 결정"에 **확정 / 탈락안 / 근거**로 남깁니다 —
  무엇을 왜 버렸는지가 남아야 같은 논의를 반복하지 않습니다
- 결과가 바뀌었으면 `research/` 본문에 재실행 시점과 무엇이 달라졌는지를 적습니다
- 진행 이력은 `ROADMAP.md`가 듭니다

보관 폴더는 **읽히지 않으면서 검색만 오염시킵니다.** 같은 주제의 문서가 두 벌이 되면
어느 쪽이 현재인지 판별해야 하고, 낡은 쪽을 현재로 착각하는 사고가 생깁니다.
지난 버전이 정말 필요하면 git 이력에 있습니다.

## 수치를 적을 때는 데이터 기간을 함께 적는다

**시세는 언제든 재수집돼 같은 파일명에 덮어쓰입니다.** 기간이 바뀌면 신호 수도 성적도 바뀌므로,
기간이 없는 수치는 나중에 **맞는지 틀린지 판별할 방법이 없습니다.**

- 수치를 담은 문서는 **머리말에 데이터 기간(시작일 ~ 종료일)과 행 수**를 적는다.
  **종료일(= 데이터 기준일)만 적으면 부족하다** — 시작일이 달라져도 결과가 달라진다
- 파일이 여럿이면 **파일마다** 적는다. 파일별로 기준일이 다르면 다른 대로 적는다
- **판정 구간을 따로 자른 검증은 데이터 기간과 판정 구간을 둘 다 적는다.**
  (예: 파일은 2002-10-14 부터인데 신호 판정은 2008 부터 — 앞 구간은 순위 축적에만 쓰인다)
- 재수집해 덮어쓴 뒤에는 **새 기간과 무엇이 달라졌는지**를 그 수치를 쓴 문서에 적는다
- 문서에 적는 값은 **그 문서가 측정할 때의 기간**이다. 지금 파일의 기간으로 갱신하지 않는다 —
  재실행하지 않았는데 기간만 바꾸면 문서가 거짓말을 한다

표기는 머리말 인용 블록 안에 `> **데이터 기간**: <대상> **시작 ~ 종료** (N 거래일)` 형식으로 둔다.

## 스펙과 결과의 분리

한 검증에 대해 **설계는 `spec/`, 결과는 `research/`** 로 나눈다.

- 설계를 바꾸면 `spec/`을 갱신하고 변경 사유를 "확정된 설계 결정"에 남긴다
- 데이터를 갱신해 재실행하면 `research/`만 바뀐다
- 실측으로 알게 된 데이터 소스의 성질(라이브러리 동작, 품질 문제)은 `spec/`의 "데이터 실측 기록"에 쌓는다.
  기억이 아니라 실측으로만 고친다

## 계획서

- 작성·갱신 절차는 `/verify-plan` 스킬이 SoT다.
- **살아있는 문서에서 계획서를 링크하지 않는다.** 계획서는 주기적으로 삭제되므로 링크가 깨진다.
  필요한 내용은 복사해 살아있는 문서가 자립하게 만든다.
- **Done 처리 전에 근거를 살아있는 문서로 승격한다.** 판단 기준은
  "이 계획서를 지금 지워도 잃는 것이 없는가". 승격 목적지는 `docs/ROADMAP.md` "계획서의 수명"이 SoT다.
