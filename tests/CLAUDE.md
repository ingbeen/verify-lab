# tests 폴더 가이드

> CRITICAL: 테스트 작성/수정 전에 이 문서를 반드시 읽어야 합니다.
> 프로젝트 전반의 공통 규칙은 [루트 CLAUDE.md](../CLAUDE.md)를 참고하세요.
> 저장소를 가리지 않는 테스트 규칙은 전역 `~/.claude/rules/python-tests.md` 가 정합니다. 이 문서에는 이 저장소 고유의 것만 둡니다.

## 파일 구성

```
tests/
├── CLAUDE.md       # 테스트 규칙 (이 문서)
├── conftest.py     # 공통 픽스처
└── test_*.py       # 이름이 검사 대상을 말한다 (test_<계층>_<모듈> · 수집기는 test_<모듈>)
```

**짝 모듈이 없는 테스트는 계층·문서를 가로지르는 계약 검사입니다** — `test_layer_contracts.py`·
`test_output_contract.py`(계층 간 계약), `test_index.py`·`test_research_docs.py`(문서 구조),
`test_tracks.py`(레지스트리를 INDEX 와 대조), `test_validate_project.py`(루트 스크립트).

`__init__.py`를 포함하지 않습니다 (src 패키지와의 이름 충돌 방지).
pytest 설정은 루트 `pytest.ini`가 Single Source of Truth이며, 실행 명령어는 `docs/COMMANDS.md`를 참고합니다.

## 1. 이 프로젝트에서 반드시 있어야 하는 테스트

측정 도구는 **틀려도 결과가 그럴듯해 보인다**는 것이 가장 큰 위험입니다.
아래 세 종류는 기능 테스트보다 우선합니다.

### look-ahead 감시 테스트 (필수)

미래 데이터를 참조하면 성과가 실제보다 좋게 나오고, 눈으로는 발견되지 않습니다.

- **뒤를 잘라낸 입력과 전체 입력의 판정 결과가 같아야 한다**를 확인합니다
  (D일까지의 신호 판정은 D+1 이후 데이터가 있든 없든 동일해야 함)
- **새 이벤트 정의를 추가할 때마다 이 테스트를 함께 추가합니다.** 예외 없습니다
- 실제 작성 예시: `reference/test_examples/event_study_test_example.py`

### 산식 고정 테스트 (필수)

정의가 곧 결론을 만듭니다. **손으로 계산한 예시로 값을 박아둡니다.**

- forward return (종가 기준·익일 시가 기준 각각)
- 초과수익, 베이스라인 3종
- 확장창 순위 판정 (판정 시점까지의 데이터만 쓰는가)
- 구간 끝이 데이터를 넘어갈 때의 처리와 **제외 건수 반환**

### 표본 보존 테스트 (필수)

표본이 조용히 사라지면 생존편향이 생깁니다.

- 입력 신호 수 = 집계된 표본 수 + 제외된 표본 수 가 항상 성립하는지
- 제외 사유별 건수가 반환되는지

## 3. 파일 격리

- 일반 규칙(import 시점에 캡처한 경로 상수 · 묶음 상수의 patch)은 `python-tests.md` 「파일을 격리한다」. 이 저장소의 예: `meta_manager` 가 들고 있는 경로 · `ETF_TARGETS = (ETF_BASE, ETF_LEVERAGE)`
- 픽스처 작성 예시: `reference/test_examples/conftest_qbt_example.py` (`mock_storage_paths`)

### 예외 — 폴더의 «실재만» 보는 검사 (읽지도 쓰지도 않는다)

**이 절의 취지는 테스트가 실제 파일 · 실제 storage 에 영향을 주지 않는 것입니다.**
그래서 **파일을 열지도 쓰지도 않고 폴더 이름의 실재만 확인하는 검사**는 예외로 허용합니다.

- 허용: `Path.is_dir()` · `iterdir()` 로 **이름 목록만** 얻는 것
- 금지: 그 경로의 파일을 **읽거나 쓰거나 지우는 것**. 여기에는 예외가 없습니다

**왜 필요한가**: 잡아야 하는 대상이 **「이 저장소의 실제 상태」**라 격리된 합성 데이터로는
잡을 수 없습니다. `tests/test_index.py`·`tests/test_research_docs.py` 가 실제 문서 경로의
실재를 검사하는 것이 그 경우입니다 — 틀린 진입점은 없는 것보다 나쁘고, 그 부패는
문서가 늘어날수록 반드시 생깁니다.

---

### 합성 시세 생성기는 파일마다 따로 둡니다 (2026-09-11 판정)

`conftest.py` 로 합치지 않습니다 — 파일마다 **내용이 다릅니다**(심는 신호 위치·기간·반환형).
겹치는 것은 시세 스키마뿐이고, **그 스키마가 바뀌면 로더 검증이 시끄럽게 실패**하므로
조용한 드리프트가 생기지 않습니다. 합치면 한 테스트의 사정으로 고칠 때 다른 파일이 함께 흔들립니다.

> **픽스처를 공유할지의 기준은 「같은 것을 만드는가」이지 「비슷해 보이는가」가 아닙니다.**

## 5. 픽스처가 코드와 같은 가정을 하면 그 버그는 영원히 안 잡힙니다

일반 규칙은 `python-tests.md` 같은 항목. 이 저장소에서 보합을 섞은 여집합 계약은
`tests/test_measure_statistics.py` 의 여집합 테스트가 고정합니다.

### 공유 계층의 테스트는 «자기 픽스처»를 갖는다

공유 계층은 자기를 쓰는 쪽을 몰라야 하고(계층 계약) **그 계층의 테스트도 같다.** 테스트가 매매법의
`constants.py` 에서 값을 빌려 쓰면 그 매매법을 지우는 순간 공유 계층의 검사가 함께 무너진다 —
`[실측] 2026-09-22` 매매법 둘을 지우자 `measure/calendar_*` 의 테스트가 만기 규칙 값과 구간 표지를
지워진 매매법에서 가져오고 있어 함께 깨졌다. 값 자체는 매매법이 갖는 것이 맞고, **틀린 것은 테스트가 그 값을 빌려 쓴 것**이다.

**픽스처는 실제 쓰이는 값과 «다르게» 고른다.** 쓰는 쪽이 모두 셋째 금요일이면 그 값만 검사하게 되므로,
픽스처에 둘째 목요일을 두어 「셋째」와 「금요일」이 하드코딩돼도 걸리게 한다.
